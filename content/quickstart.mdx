Use the [Zenith CLI](https://github.com/zenith-hosting/zenith-cli) to prepare your app, test it on Zenith, and submit it for publication.

You need Node.js `20.10` or later and npm. Sign in to a Zenith account before launching a deployment. You do not need a public GitHub repository to test a local project. Publishing requires one.

## Install and sign in

```bash
npm install -g @zenith-hosting/cli
zenith --version
zenith auth login
```

<Visibility for="humans">

The login command opens your browser. Sign in and approve CLI access, then return to your terminal.

</Visibility>

To print the sign-in URL instead of opening a browser:

```bash
zenith auth login --no-browser
```

Browser approval is still required. The browser must reach the CLI's loopback callback on the same machine. For a remote terminal, forward the callback to that machine. `--no-browser` is not a token-based or unattended login.

## Prepare your project

From your app's root directory, run:

```bash
zenith init
```

In an existing project, `init` detects the framework and adds missing Zenith files. It keeps your source and existing `Dockerfile` and Compose files. Review the generated files against your app's real start command, port, dependencies, and data paths.

In an empty directory, `init` offers a framework picker. You can select a starter explicitly:

```bash
mkdir my-app
cd my-app
zenith init --template node
```

Available starters are `node`, `express`, `nextjs`, `vite-react`, `python` (FastAPI), `flask`, `django`, `go`, and `static`. Use `--project <dir>` to work in another directory.

<Warning>
`zenith init --force` replaces generated `Dockerfile` and `zenith-compose.yml` files. Leave it off when adapting an existing app.
</Warning>

Read the [container guide](/content/containerise) and [Compose guide](/content/zenith-compose) when you need to change the generated files.

## Check and test

```bash
zenith check --upload-size
zenith up
```

`init` and `check` work offline. `check` validates the preview policy and local environment file. `--upload-size` also checks archive size. It does not build or run your app.

`up` uploads your local project, builds it on Zenith, and prints a temporary URL when it is ready. You do not need to build or push a container image yourself. Test the app at that URL, then stop it:

```bash
zenith logs --source runtime
zenith down
```

See [temporary deployments](/content/up) for lifetime, upload limits, secrets, logs, and troubleshooting.

## Publish when ready

Commit and push your app to a public GitHub repository. Include a root `Dockerfile` and `zenith-compose.yml`, even if you use prebuilt images. Then start the publishing flow:

```bash
zenith publish
zenith publish status
```

Publishing submits a pinned commit for review. It does not make the app available in the marketplace immediately. See [Publish your app](/content/publish) for authorization, listing files, screenshots, and updates.

## Run a non-interactive agent session

Set `NO_COLOR=1` for plain, agent-readable progress instead of animated output. Run commands without a TTY and supply any required inputs explicitly:

```bash
export NO_COLOR=1
zenith init --template node </dev/null
zenith check --upload-size </dev/null
zenith up </dev/null
zenith logs --source runtime </dev/null
zenith down </dev/null
```

Choose the template that matches the app; `node` is only an example. Do not overwrite existing app behavior to fit a starter.

`NO_COLOR=1` controls output. It does not disable every prompt or approve external actions. Omit `--verbose` and do not set `ZENITH_VERBOSE=1`, which enables animated output. Use explicit `--template` and publishing inputs instead of relying on terminal prompts.

Reuse authorized CLI credentials. If login is needed, use `NO_COLOR=1 zenith auth login --no-browser` and hand the URL to the user. Do not copy browser cookies or try to bypass OAuth, GitHub connection, or the Developer Agreement.

Before `up`, confirm that uploading the project and creating a temporary deployment are within the user's request. Review archive inputs and keep secrets out of source and image layers. Do not push commits, publish images, change registry visibility, or submit an app without explicit authorization.

After testing, report the session ID, URL, expiry, commands run, app flows verified, and cleanup result. Record the tested commit and any local changes. A ready URL alone does not prove that the app works. Follow the [publishing agent workflow](/content/publish#agent-publishing-workflow) only when submission is authorized.

</Visibility>
