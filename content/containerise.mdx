The CLI can build your app on Zenith. You do not need to publish an image to a registry before using `zenith up` or publishing an app with `build: .`.

| Workflow | Build source |
| --- | --- |
| `zenith up` | Your uploaded local project. Requires one app with `build: .` and a root `Dockerfile`. |
| `zenith publish` with `build: .` | The pinned public GitHub commit. Zenith reuses a verified matching preview image or builds the commit before review. |
| Publishing an app with `image` | An existing image that Zenith can pull without registry credentials. |

<Info>
A root `Dockerfile` is required for `build: .`. Image-only submissions use the declared public images and do not require a Dockerfile.
</Info>

Image-based dependencies, such as Postgres or Redis, must also be publicly pullable. Zenith reuses a preview image only after verifying that its source matches the pinned publish commit.

## Prepare a Dockerfile

From your app's root directory, run:

```bash
zenith init
```

The CLI adds missing files for a detected or selected framework. It preserves an existing `Dockerfile` and `zenith-compose.yml` unless you use `--force`. Reuse your production Dockerfile where possible. Review the generated start command, port, build steps, and runtime dependencies.

## Check the runtime

Use images that support `linux/amd64`. Configure HTTP services to listen on `0.0.0.0`.

Configure each service to:

- Write logs to `stdout` and `stderr`.
- Start without host-mounted source files.
- Read deployment-specific values and secrets from environment variables.
- Store persistent data in declared volumes.

Use [static configuration files](/content/static-configuration) for static, non-secret files. Record the app's listening port, health endpoint, required variables, and data paths in `zenith-compose.yml`.

<Warning>
Do not copy `.env` files, private keys, or registry credentials into an image. Use a gitignored `.env.local` for [preview secrets](/content/up#supply-test-secrets) and `x-zenith.env` for [environment variables and secrets](/content/environment-variables).
</Warning>

For a Zenith-built app, set `build: .` on one service and do not also set `image`. Other services need public `image` references. Zenith prepares the image before submission. It does not run Compose builds during deployment.

## Test the build on Zenith

```bash
zenith check --upload-size
zenith up
zenith logs --source build
zenith logs --source runtime
```

`check` validates preview policy. It does not build the image. `up` builds the root `Dockerfile` using the uploaded project. Preview builds do not support alternate Dockerfiles, build arguments, build targets, remote contexts, or bind mounts. See [temporary deployments](/content/up) for the complete workflow.

After testing, run:

```bash
zenith down
```

## Use an existing image

For image-based publishing or dependency services, set `image` to an anonymously pullable tag or digest. Pin a version rather than relying on a moving `latest` tag. An image-only app can be published, but it does not meet the preview requirement for one built app service.

If you maintain the image yourself, publish it to a registry that permits anonymous pulls. Verify its visibility before submitting the app.
