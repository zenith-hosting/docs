`zenith-compose.yml` is a Compose Specification file with a required top-level `x-zenith` block for Zenith listing and deployment metadata.

Every service needs a public container image. If you do not have one yet, [containerise your app first](/content/containerise).

## Create the file

Add `zenith-compose.yml` to the root of your app's repository. If you already have one, start from the Compose file you use to run the app.

This example packages PrivateBin with one public service and one persistent volume:

```yaml zenith-compose.yml
x-zenith:
  catalog:
    name: PrivateBin
    description: A minimalist, open-source online pastebin.
    authors:
      - PrivateBin contributors
    tags:
      - pastebin
      - privacy
    source: https://github.com/PrivateBin/PrivateBin
    license: AGPL-3.0
    alternatives: ["Pastebin"]
    website: https://privatebin.info
  expose:
    - service: privatebin
      port: 8080
      label: web
      web: true
  storage:
    data:
      volume: privatebin_data
      label: Encrypted paste data
      description: Server state and encrypted paste records.
      public: false

services:
  privatebin:
    image: ghcr.io/privatebin/nginx-fpm-alpine:2.0.6@sha256:13290e2f04bfd98cf8fc7e8d216fb76b2b2d12373d4923b859cd41c2d984fde8
    ports:
      - "8080:8080"
    volumes:
      - privatebin_data:/srv/data

volumes:
  privatebin_data:
```

The schema requires `services` and `x-zenith`. Inside `x-zenith`, `catalog` requires `name`, `description`, `authors`, `tags`, `source`, and `license`; `expose` must contain at least one entry. The remaining catalogue fields and blocks are optional.

## Configure the listing

Set the catalogue metadata in `catalog`. The schema requires every field marked **Yes**.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | Yes | App name. |
| `description` | string | Yes | Short app description. |
| `authors` | list of strings | Yes | One or more unique author names. |
| `tags` | list of strings | Yes | One or more unique tags. |
| `source` | URI | Yes | Source repository or project URL. |
| `license` | string | Yes | License identifier or name. |
| `alternatives` | list of strings | No | Comparable apps. |
| `detail` | string | No | Additional catalogue detail. About 3-5 sentences long. |
| `funding` | URI | No | Funding URL. |
| `website` | URI | No | Project website. |

## Expose a service

`expose` maps a Compose service port to a public Zenith hostname.

```yaml
x-zenith:
  expose:
    - service: web
      port: 3000
      web: true
```

Each entry has these fields:

| Field | Value |
| --- | --- |
| `service` | Compose service name. Required. |
| `port` | Service port from `1` through `65535`. Required. |
| `label` | Optional route label. It must start with a lowercase letter or digit and contain only lowercase letters, digits, and hyphens. |
| `web` | Boolean marker for whether the service is user-facing. Required, even when `false`. |

## Add deployment variables

`env` declares values Zenith resolves for each deployment. The map key becomes the literal container environment variable name.

### Use the public URL

A bare string aliases another declared value or a Zenith built-in:

```yaml
x-zenith:
  env:
    APP_URL: ZENITH_PUBLIC_URL
    APP_HOST: ZENITH_PUBLIC_HOST
```

Common built-ins include:

| Name | Value |
| --- | --- |
| `ZENITH_PUBLIC_URL` | Verified custom URL, or the deployment's Zenith URL. |
| `ZENITH_PUBLIC_HOST` | Public URL authority, including a port when present. |
| `ZENITH_PUBLIC_HOSTNAME` | Public hostname without a port. |
| `ZENITH_OWNER_EMAIL` | Account email when available. |
| `ZENITH_SMTP_HOST` | Hosted SMTP server. |
| `ZENITH_SMTP_PORT` | Hosted SMTP port. |
| `ZENITH_SMTP_USER` | Deployment SMTP username. |
| `ZENITH_SMTP_PASS` | Deployment SMTP password. |

### Generate a stable secret

Use `generate` with an RE2 pattern. Zenith creates the value once and keeps it for the life of the deployment.

```yaml
x-zenith:
  env:
    APP_SECRET:
      generate: '([A-Za-z0-9]{11})([A-Za-z0-9]{11})([A-Za-z0-9]{11})([A-Za-z0-9]{11})'
      input:
        label: App secret
        secret: true
```

The pattern must be a non-empty string. Changing the pattern does not rotate a value that a deployment already stores. `generate`, `template`, and `alias` are mutually exclusive.

### Build a value from other variables

Use `template` to substitute `{NAME}` references on every render:

```yaml
x-zenith:
  env:
    API_URL:
      template: '{ZENITH_PUBLIC_URL}/api'
```

Add `services` to inject a value into selected Compose services. Without it, Zenith injects the value into every service.

```yaml
x-zenith:
  env:
    DATABASE_PASSWORD:
      generate: '([A-Za-z0-9]{11})([A-Za-z0-9]{11})([A-Za-z0-9]{11})([A-Za-z0-9]{11})'
      services:
        - web
        - database
```

An `x-zenith.env` value replaces a Compose `environment` entry with the same name in the services it targets.

## Add persistent storage

`storage` describes a Compose named volume.

```yaml
x-zenith:
  storage:
    uploads:
      volume: app_uploads
      label: Uploaded files
      description: Images and documents uploaded by app users.
      public: true

services:
  app:
    volumes:
      - app_uploads:/app/uploads

volumes:
  app_uploads:
```

| Field | Value |
| --- | --- |
| `volume` | Top-level Compose volume name. Required. It must contain only letters, digits, `.`, `_`, or `-`. |
| `label` | Name shown to the app owner. Optional. |
| `description` | Description of the stored data. Optional. |
| `public` | Gives the app owner file-manager access when enabled. Optional, defaults to `false`. |

<Warning>
Do not mark database files, indexes, credentials, or other application internals as public storage. `public: true` makes the volume eligible for app-owner file-manager access.
</Warning>

## Add static configuration

Use standard Compose `configs` with inline `content` when your app needs a static, non-secret file. Declare the file at the top level, then reference it from each service that needs it.

Prefer this to an init container or shell entrypoint that only writes a fixed file. You do not need a shell in the app image, an adjacent config file, or a bind mount.

This complete example runs Gatus with a status check and persistent SQLite history:

```yaml zenith-compose.yml
x-zenith:
  catalog:
    name: Gatus
    description: Monitor endpoints and publish a status page.
    authors:
      - TwiN
    tags:
      - monitoring
    source: https://github.com/TwiN/gatus
    license: Apache-2.0
  expose:
    - service: gatus
      port: 8080
      web: true
  storage:
    history:
      volume: gatus_data
      label: Monitor history
      description: SQLite history of endpoint checks.

services:
  gatus:
    image: ghcr.io/twin/gatus:v5.36.0
    environment:
      GATUS_CONFIG_PATH: /config/config.yaml
    configs:
      - source: gatus-config
        target: /config/config.yaml
        mode: 0444
    volumes:
      - gatus_data:/data
    ports:
      - "8080:8080"

configs:
  gatus-config:
    content: |
      storage:
        type: sqlite
        path: /data/data.db
      endpoints:
        - name: cloudflare
          url: https://www.cloudflare.com
          interval: 60s
          conditions:
            - "[STATUS] == 200"

volumes:
  gatus_data:
```

Gatus reads `/config/config.yaml` from a read-only config mount. Its check history stays on the separate `gatus_data` volume. Only services that reference `gatus-config` receive the file.

Zenith supports inline `content`, short service references, and long references with `source`, `target`, and optional `mode`. File-backed and external config sources are unsupported. See [Compose configs](/content/zenith-compose-reference#compose-configs) for defaults and validation rules.

<Note>
Standard Compose `configs` is a top-level map next to `services`. It is not the reserved `x-zenith.configs` metadata block.
</Note>

When Zenith applies an updated config definition, it restarts the services that consume the changed content. It does not update a running process's mounted file in place. Pushing a Git commit does not automatically update an existing deployment.

<Warning>
Do not put passwords, tokens, or private keys in `configs.content`. Use deployment environment values for secrets. Zenith does not substitute `x-zenith.env` values into config content.
</Warning>

If your app supports its own environment expansion in config files, declare its variables and write `$$` wherever Compose must preserve a literal `$` for the app. Keep a startup adapter when you need runtime-generated content or a writable config file. Keep database setup and dependency health checks separate from static file delivery.

## Check the file locally

Ask Docker Compose to parse the file:

```bash
docker compose -f zenith-compose.yml config
```

Then run the app:

```bash
docker compose -f zenith-compose.yml up -d
```

These commands test the Compose model and the app. Zenith runs the `x-zenith`-specific validation during submission.

<Check>
Continue when Compose parses the file without errors, every service stays running, and each exposed service answers on its declared port.
</Check>

## Zenith runtime restrictions

The schema accepts standard Compose features that Zenith's deployment path does not support. Passing schema validation does not guarantee that the app can deploy.

<Warning>
Prepare one self-contained file for Zenith. Developer submissions cannot use:

- Bind mounts.
- Top-level `include`.
- Config sources other than inline `content`, including `configs.<name>.file`, `external`, and `environment`.
- Config ownership overrides (`uid` or `gid`) or targets that collide with another mount.
- `secrets.<name>.file`.
- Service `extends`, `env_file`, or `label_file`.

Every service needs a public `image`; Zenith does not run Compose `build` during deployment. `privileged: true` triggers a security warning during review.
</Warning>

## Commit the file

Commit `zenith-compose.yml` at the repository root on the default branch. The file must be non-empty and no larger than `128 KiB`.
